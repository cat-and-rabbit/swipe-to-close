# スワイプで新規タブを閉じる機能の修正計画

作成日: 2026-09-12

状態: 完了。実装・自動テスト41項目・配布ZIPの作成と検証を完了し、2026-09-12にユーザーの最終版での実機確認を受領。詳細は [検証記録](verification.md) を参照。

## 目的と完了条件

リンクを新しいタブで開いた後、リンク先をクリックせずに、macOS の「戻る」方向の2本指スワイプでそのタブを閉じられるようにする。

| 条件 | 期待する動作 |
|---|---|
| ⌘クリック、中クリック、右クリックの「新しいタブで開く」、target="_blank"、window.open | 新しいタブを対象として認識する |
| 開いたページをクリックせず、そのままスワイプ | 対象タブだけを1回閉じる |
| 開いたページで縦スクロールしてからスワイプ | 同様に閉じる |
| タブ内で別ページ・別サイトに移動した後に戻る | 通常どおり前の履歴に戻る |
| 元の履歴位置まで戻ってから、もう一度スワイプ | 対象タブを閉じる |
| 縦スクロール、横スクロール領域の操作、ピンチ、途中で取り消したジェスチャー | タブを閉じない |
| ページが独自の history.state を使用する | 値や履歴件数を拡張機能が書き換えない |
| 複数タブの同時作成、Service Worker の停止・再起動 | 対象タブの情報を欠落・混同しない |

中心となる対象は新しく開かれた通常の HTTP/HTTPS ページ。空の新規タブからのURL入力も対象候補として検証する。拡張機能有効化前から存在するタブや復元タブは、起点を確実に復元できる場合にだけ対象にする。chrome://、Chrome Web Store などスクリプトを注入できないページは対象外として明記する。

## フェーズ1: 最小試作で実現方式を決める

実装全体の変更前に、最も不確かな「クリック前の本物のスワイプ」を検証する。

1. 現行版と最小試作版を、独立した検証用プロファイルで比較できるようにする。前回の Chrome for Testing 149 に加え、実際に使用する通常版ChromeのバージョンとmacOSのジェスチャー設定を記録する。
2. 第一候補として、content script で横方向の wheel イベント列を観測する試作を作る。最初はイベントの方向・量・時刻・cancelable・既定動作の抑止状況を記録し、判定結果を表示する。
3. 本物のトラックパッドで、クリック前の戻るスワイプ、縦スクロール、横スクロール、ピンチ、途中キャンセル、慣性、ナチュラルスクロール設定の差を確認する。wheel の受信・キャンセル可能性と通常のブラウザ履歴移動との関係を確認する。
4. テストタブだけを閉じる試作に進め、1ジェスチャーにつき1回だけ閉じ、続く慣性入力が切替先のタブを閉じないことを確認する。
5. 起点の履歴項目を識別する試作も行う。Navigation API の currentEntry.key と、拡張機能側のページ遷移情報の組み合わせを候補にする。リロード、replaceState、pushState、ハッシュ移動、異なるオリジンからの戻り、BFCache復元で識別が維持できるかを調べる。

**採用条件:** 通常版Chromeと物理トラックパッドで、クリック不要のクローズ・通常ナビゲーション・誤クローズ防止を確認できること。合成wheelイベントや history.back() の成功だけでは採用しない。

wheel はmacOSのネイティブなスワイプ完了通知と同一ではないため、直接検出方式が成立するとはまだ断定しない。成立しない場合は本実装へ進まず、制約と代替案を具体化する。ネイティブ補助アプリや操作方法の変更が必要なら、追加要件として提示する。

成果物: 検証用拡張、操作記録、採用する方式・対象範囲・既知の制限を記した設計メモ。

## フェーズ2: タブ単位の状態管理を実装する

主な変更先: background.js、必要に応じてタブ状態を管理する小さなモジュール。

- tab.url が空かどうかだけの新規タブ判定を廃止する。tabs.onCreated と、必要なら webNavigation.onCreatedNavigationTarget / onCommitted を組み合わせ、新規タブの作成と最初のナビゲーションを対応付ける。
- openerTabId は補助情報として使う。openerの有無だけで、noopenerを含む新規リンクタブを除外しない。
- タブごとに「判定中」「対象」「対象外」「クローズ処理中」を管理する。対象タブでは起点の履歴識別情報、現在のトップフレームdocumentId、状態の世代を保持する。
- 保存先は拡張機能の chrome.storage.session とし、`tab:<id>` のようなタブ別キーを使う。共有配列全体の読み書きをやめる。
- 同じタブへの更新は順序付けする。初期化要求は必要な登録・状態読み込みの完了を待つ。一定時間で確定できない場合は「対象外」と混同せず、再同期できる状態にする。
- Service Worker起動時は保存状態の読み込み完了後に処理する。リスナーの登録は同期的に行う。
- onRemoved、タブ置換、古いページからの遅延メッセージを扱う。クローズ要求では対象タブ・現在のドキュメント・状態の世代を確認する。

完了条件: 同時作成・同時削除・登録前問い合わせ・Worker再起動でも状態が欠落せず、別のタブや古いページの要求で閉じない。

## フェーズ3: 起点の判定とスワイプ処理を実装する

主な変更先: content.js、必要に応じてジェスチャー判定モジュール。

- フェーズ1で成立した方式を実装する。直接検出方式を採用した場合は、拡張機能による replaceState / pushState とページ側 sessionStorage の初期化フラグを撤去する。
- 起点の履歴項目をタブ単位で一度確定する。異なるサイトに移動しても、そのサイトを新しい起点として登録しない。
- 起点はURLの一致や history.length だけで判断しない。Navigation APIでページから見える履歴にもオリジンによる制限があるため、canGoBack=false だけを「タブ全体の履歴先頭」と扱わない。
- 通常の履歴位置ではChromeのスワイプによるナビゲーションを妨げず、確認できた起点だけで閉じる処理を有効にする。起点を確認できない場合は閉じない。
- 初回のHTTPリダイレクト、JavaScriptリダイレクト、location.replace、リロード、SPA、ハッシュ移動、BFCache復元を個別に扱う。履歴が追加された移動と置換された移動を区別する。
- 方向、横・縦の比率、累積移動量、時間、逆方向への切り返し、修飾キーを使ってジェスチャーを判定する。閾値は実機記録から決め、マウスホイール入力も誤って閉じないか確認する。
- 横スクロール可能な祖先要素やページ側の操作領域との競合を検証する。iframe上を操作した場合の受信範囲も確定し、未対応領域は明記する。
- ジェスチャー成立時にクローズを一度だけ要求する。タブ切替後まで続く入力に備え、複数タブにまたがる連続クローズも防ぐ。

完了条件: 起点ではクリックなしで閉じ、起点以外では通常の戻るが働き、ページの履歴とstorageを変更しない。

## フェーズ4: 回帰テストと実機受け入れ確認

意味のある不具合再現ケースを、自動テストと手動検証に分けて残す。

| 検証方法 | 対象 |
|---|---|
| Node.js等によるロジックテスト | 同時更新、問い合わせの競合、同一タブ更新の順序、古いメッセージ、重複クローズ、保存状態の再読込 |
| 拡張機能を読み込んだブラウザテスト | 各種リンクの開き方、opener/同一サイトのフラグ複製、異なるサイトへの往復、SPA、リダイレクト、リロード、BFCache、履歴データの保持 |
| 通常版Chromeと物理トラックパッド | クリック前とスクロール後のクローズ、スワイプ方向、途中キャンセル、横スクロール、ピンチ、慣性、タブ切替直後の誤動作 |

- 少なくとも8タブ以上の同時作成を繰り返し、作成した全対象タブと保存状態が一致することを確認する。
- 異なるサイトでの「戻る」は前ページに戻り、起点に戻った後の次のスワイプだけが閉じることを確認する。
- 自動テストの状態観測ではページにユーザーアクティベーションを与えない。
- 実機スワイプは開発者/利用者による手動チェックを完了条件に含める。未実施なら修正完了として扱わない。

成果物: 再実行できるテスト、操作手順、使用したChrome/macOSのバージョンと結果。

## フェーズ5: 説明・設定・配布物を整える

主な変更先: README.md、docs/index.md、docs/privacy-policy.md、manifest.json。

- READMEの「リンクからの新規タブは対象外」「リンク元の履歴を継承」「history.length === 1 のみ」を、確定した実装に合わせて修正する。
- 通常ナビゲーション、起点の扱い、対象外ページ、復元タブ、iframe等の制限を実測結果に合わせて記載する。
- 直接スワイプ検出を採用する場合、現在READMEにある「戻るボタンやショートカットでも閉じる」の維持可否を明記する。スワイプ以外の操作で閉じることは、今回の必須受け入れ条件には含めない。
- 実際に使用するAPIに合わせて権限を整理し、tabsの説明を修正する。webNavigationを追加する場合は用途も記載する。
- 採用APIに必要な minimum_chrome_version を設定する。デバッグ用の記録を通常動作から外し、プライバシーポリシーを実装に合わせる。
- バージョンを更新し、READMEのzip名を合わせる。配布zipには実行に必要なファイルだけを含め、新しい検証用プロファイルへ読み込んで確認する。
- Chrome Web Storeへの公開は、この計画の成果物を確認した後の別作業とする。

完了条件: テスト済みの挙動・説明・権限・配布ファイルが一致する。

## 実行順序

フェーズ1の方式決定 → フェーズ2の状態管理 → フェーズ3の起点とジェスチャー → フェーズ4の受け入れ確認 → フェーズ5の配布準備。

実装時のコミットは、方式検証・状態管理と競合修正・ジェスチャーと起点判定・テストと資料整備に分け、各変更を独立して確認できるようにする。所要時間はフェーズ1の実現性確認後に見積もる。

## 判断に使用する一次資料

- [Chromiumの履歴スキップ仕様](https://chromium.googlesource.com/chromium/src/+/main/docs/history_manipulation_intervention.md): 現行の履歴挿入方式で、ブラウザの戻るとhistory.back()の挙動が異なる理由。
- [Chrome webNavigation API](https://developer.chrome.com/docs/extensions/reference/api/webNavigation): 新規ナビゲーション先、コミット、履歴更新、ドキュメント識別のイベント。
- [HTML Navigation API](https://html.spec.whatwg.org/multipage/nav-history-apis.html#navigation-api): 起点となる履歴項目の識別方式を検証する際の仕様。
- [Pointer Events仕様](https://w3c.github.io/pointerevents/): wheelイベントの挙動を確認するための資料。実際のmacOSスワイプの成立可否は実機で判断する。
